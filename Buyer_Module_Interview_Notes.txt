2) HIGH-LEVEL ARCHITECTURE (HOW INTERVIEWER MAY EXPECT YOU TO EXPLAIN)
============================================================
Pattern in use:
- ASP.NET Core MVC pattern (Controller + Razor Views + EF Core DbContext)
- Session-based active user resolution (not claims-based in buyer flow)

Request flow pattern used repeatedly:
1. Browser hits buyer endpoint (example: /BuyerMarketplace)
2. Controller calls GetActiveBuyer() using Session key "UserUsername"
3. If buyer not found => RedirectToAction("Login", "Auth")
4. Controller queries SQL via EF Core (_context)
5. Controller prepares ViewBag/ViewData + model
6. Razor view renders UI

Data flow style:
- Heavy use of Include/ThenInclude for eager loading nested navigation properties
- ViewBag for summary sections/tabs/cards
- Strongly-typed models for forms/reports/invoices

============================================================

- Buyers, CropListings, CropOrders, Wishlists, Notifications, Harvests, Farmers, Users

Important mappings (SmartFarmDbContext):

  - FK HarvestId -> Harvest
  - Optional FK BuyerId -> Buyer
  - AvailableQuantity, OriginalQuantity, PurchasedQuantity

  - Optional ListingId, Optional HarvestId
  - Required BuyerId, Required FarmerId
  - status + invoice + GST + decline fields
- Notification:
  - FK UserId -> User
- Wishlist:
  - BuyerId + optional CropId + optional FarmerId + NotifyWhenAvailable

Schema hardening helper:
- _context.EnsureMarketplaceColumnsExist() called in BuyerMarketplace/Index
- Adds missing columns if absent:
  - CropListing.OriginalQuantity
  - CropOrder.DeclineReason, DeclineNotes, DeclinedDate

Interview point:
- This is runtime schema safety fallback in addition to migrations.

A) Dashboard (/Buyer/Dashboard)

D) Reports (/Buyer/Reports)

E) Transactions (/Buyer/Transactions)
- Filters only payment-relevant statuses

F) Wishlist (/Buyer/Wishlist)

G) Notifications endpoints
- GET Buyer/GetNotifications => JSON for bell dropdown

6) BUYER MARKETPLACE FLOW NOTES
============================================================
A) Index (/BuyerMarketplace)

- Lists farmers + buyer saved farmer IDs

- Else => add new wishlist record

E) ToggleNotifyMe POST
- Finds or creates wishlist item by BuyerId+CropId
- Toggles NotifyWhenAvailable

7) BUYER ORDER FLOW NOTES (CORE INTERVIEW AREA)
============================================================
A) Order list (/BuyerOrder)
- Gets all buyer orders
- Splits to tabs by status:
  - Requests
  - Active
  - Declined
  - Completed
- Builds sequential order map

B) Order details (/BuyerOrder/Details/{id})
- Loads full order graph and timeline data
- Declined orders show reason/notes/date
- Non-declined orders show shipment stepper

C) PlaceOrder GET (checkout screen)
- Supports 2 paths:
  1) Listing purchase (listingId)
  2) Harvest prebook (harvestId)
- Validates availability and quantity limits
- Calculates subtotal + GST (5%) + total

D) PlaceOrder POST
- Current active logic places order in PENDING_FARMER_ACCEPTANCE
- Creates invoice number format INV-{year}-{random}
- Saves order + notifies farmer
- Redirects to order index with "awaiting farmer acceptance"

E) PaymentDetails GET
- If orderId is passed:
  - Loads order
  - Blocks payment for PENDING_FARMER_ACCEPTANCE/REQUESTED
  - Allows payment once accepted
- Else:
  - Loads from TempData (legacy/alternate path)

F) ConfirmPayment POST
- If orderId path:
  - Marks order Paid
  - Updates listing purchase quantities and available stock
  - Sends farmer notification
- Else TempData path:
  - Creates new order with Status = "Request Sent"
  - Sends buyer and farmer notifications

Architectural interview observation:
- There are two payment/order paths (orderId update path and TempData new-order path), which indicates legacy flow coexistence.

G) Invoice GET
- Loads order if belongs to buyer
- Blocks invoice for Declined/Rejected/Cancelled
- Renders printable invoice view

10) IMPORTANT TECHNICAL POINTS (LIKELY ARCHITECT QUESTIONS)
============================================================
1. Why Include/ThenInclude chains are used:
   - To avoid lazy-loading assumptions and load nested data needed by views.

2. Why ViewBag is used heavily:
   - Quick binding for dashboard cards/tab datasets; could be migrated to richer typed view models.

3. Why TempData appears in payment flow:
   - Carries checkout values across redirects; includes Keep() call for next request.

4. Why anti-forgery is present:
   - POST endpoints (wishlist/payment/profile) use [ValidateAntiForgeryToken] and form tokens for CSRF protection.

5. Why invoice is blocked for declined/cancelled:
   - Business rule: no invoice for failed order lifecycle.

6. Runtime DB schema helper use:
   - Defensive compatibility for partially migrated databases.

12) TECHNICAL INTERVIEW QUESTIONS + SAMPLE ANSWERS
============================================================
Q1) How does buyer authentication context work in this module?
A1) Each action calls GetActiveBuyer(), which reads Session["UserUsername"] and resolves Buyer + User from DB. If missing, user is redirected to Auth/Login.

Q2) Why do you call EnsureMarketplaceColumnsExist at runtime?
A2) It is a defensive fallback to add critical marketplace columns if DB schema is behind. It prevents runtime failures on older databases.

Q3) Explain the difference between CropListing and CropOrder.
A3) CropListing is supply-side inventory listing (price, available quantity, status). CropOrder is transaction record (buyer/farmer, quantity, status, totals, invoice, delivery details).

Q4) How is buyer dashboard summary computed?
A4) Using EF aggregate queries: Sum(TotalAmount) for delivered orders, Count for active/completed/wishlist, and latest orders/notifications lists.

Q5) How does the marketplace filter work technically?
A5) It builds IQueryable<CropListing> and conditionally appends Where clauses from MarketplaceSearchViewModel before executing with ToList.

Q6) Why use Include/ThenInclude in marketplace and order actions?
A6) Views require deeply nested data (Crop -> CropCycle -> LandPlot -> Farm -> Farmer). Eager loading ensures those objects are available without extra lazy queries.

Q7) How is wishlist toggle implemented?
A7) It checks existing Wishlist by BuyerId + CropId + FarmerId. If found, removes it; otherwise inserts a new record.

Q8) What is NotifyWhenAvailable?
A8) A boolean on Wishlist that tracks crop stock alert subscription. ToggleNotifyMe flips this flag and creates wishlist row if missing.

Q9) Describe order lifecycle from checkout to payment.
A9) PlaceOrder POST creates order in PENDING_FARMER_ACCEPTANCE and notifies farmer. PaymentDetails blocks payment until accepted. ConfirmPayment marks order Paid and updates stock.

Q10) How is stock updated after payment?
A10) For listing orders: PurchasedQuantity increases, AvailableQuantity decreases, status becomes Sold when quantity reaches zero.

Q11) How are notifications used?
A11) Buyer and farmer notifications are inserted into Notifications table at key events: order request, payment completion, and client-side read-state updates.

Q12) Why are there two paths in ConfirmPayment?
A12) One path updates an existing accepted order via orderId. Another legacy TempData path creates a new order. This indicates phased evolution and can be consolidated.

Q13) What are the key validation controls in buyer order flow?
A13) Data annotations in CropOrderViewModel, quantity limits against listing/harvest stock, model state checks, and anti-forgery on POST endpoints.

Q14) Why can invoice be denied?
A14) Invoice action rejects Declined/Rejected/Cancelled statuses as those are non-fulfillable transactions.

Q15) What security improvement would you prioritize first?
A15) Replace plaintext password comparison/update with salted hash verification (e.g., ASP.NET Core Identity PasswordHasher).

Q16) What maintainability improvement would you suggest for status logic?
A16) Use enum or centralized constants/state machine instead of scattered string literals.

Q17) Why use ViewData/UserName/UserInitials/UserRole in every action?
A17) _BuyerLayout and sidebar UI depend on these values to render identity, role badge, and profile avatar.

Q18) How does the buyer notification bell work?
A18) _BuyerLayout has dropdown container; Buyer/GetNotifications returns JSON list and unread count; mark-as-read endpoints update IsRead.

Q19) What is the role of BuyerProfileViewModel?
A19) It isolates profile form input + validation rules from DB entity and supports file upload with IFormFile.

Q20) Why is Session used for profile picture path?
A20) Layout reads Session["UserProfilePicture"] to render topbar avatar without querying DB for every request.
